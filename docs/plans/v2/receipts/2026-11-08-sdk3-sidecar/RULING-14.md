## BLOCKING

### B1 — #590, the rollup cursor re-serves its own row. **Fix shape: serve the cursor in the ENGINE's nine-digit form and parse it with the SDK's own ns parser — both ends native, zero lore precision arithmetic. Builder: production. Servicer: the served-text round-trip pin. NOT the ceiling.**
- Root cause, stated as a class: the exclusive boundary `updated_at > $since` is exact only if `$since` carries the SAME precision as the stored stamp. Drop #34's rider ("retire iff the exclusive-boundary tests stay green") was derived over the IN-PROCESS bind (a `PreciseDatetime` keeps ns across CBOR, R6b) and never over the path every agent uses: text out (`isoformat()` → µs), text in (`fromisoformat` → µs, and — measured — it also truncates a nine-digit text silently, so "serve more digits" alone would have changed nothing). Quantifier law: the property was pinned on one member of the set.
- **Shape (R6 native principle):** `next cursor: {next_cursor.isoformat_with_nanoseconds()}` (the engine's own `…45.186697518Z`), and `_parse_rollup_since` → `surrealdb.data.types.datetime.parse_instant(text)` (1–9 fraction digits, zone or `Z`, returns a `PreciseDatetime` the CBOR encoder sends as `[seconds, nanos]`), keeping the teaching error for unparseable/naive text. Backward compatibility is free: a pre-fix µs cursor an agent still holds parses (6 digits) and re-serves at most the boundary row ONCE — say so in the fix note; no shim. **Rejected:** restoring the +1 µs ceiling — it is a hand-rolled precision patch for a mismatch lore itself creates at the text boundary, and it would re-pin the SDK-2.0 workaround R1 told us to re-evaluate; with both ends native the ceiling has no job. **Rejected:** an opaque engine-text cursor bound as `<datetime> $since` — correct too, but it moves parsing to the wire for no gain once `parse_instant` exists.
- **The class — who else hands a stamp back?** Sweep (tool params + `fromisoformat` sites): the rollup `since` is the ONLY served cursor an agent returns today; `server.py:5637` parses a STORED raw stamp for `AgeStatus` (not a hand-back; tolerant by design); `lore_diff since/until` are snapshot ids; `lore_recall as_of` exists in the backend but is NOT yet exposed — **rider for 67b (which exposes it): the same `parse_instant` parser, never `fromisoformat`, and its own round-trip leg**. Future rule, one line: any served timestamp an agent may hand back is rendered with `isoformat_with_nanoseconds` and parsed with `parse_instant` — the pair is THE cursor codec; a second codec is copy #2.
- **Pin it like this (servicer):** convert the audit's `probe_rollup_cursor_test.py` into the contract: a task stamped with a non-zero ns tail (force it: write `updated_at = d"…518Z"` through admin DML, or loop `time::now()` until `nanosecond != 0`) → rollup → take the SERVED cursor TEXT → `_parse_rollup_since` → rollup again → the row is ABSENT (`reserved=False`); control = the in-process bind leg the old pins had. Mutation: swap the parser back to `fromisoformat` ⇒ RED; swap the render back to `isoformat()` ⇒ RED. Leg 1 is then true: "everything after this cursor" means after the stamp the row carries.
- **Same class, unverified — one cheap PROBE in the fix wave, not a blocker:** `time::now()` is fixed per transaction, so N tasks transitioned in ONE transaction share one `updated_at`; with `limit < N`, `next_cursor` = that stamp and `>` skips the remainder on the next page FOREVER (the `total >= len(rows)` disclosure says "truncated" but the next page cannot reach them). If it reproduces, the honest minimal fix is a `(updated_at, id)` tiebreak or a `>=`-with-id cursor — a design change for the operator (PKT-06 cursor rules), filed as a finding with the probe as receipt; if it does not, say why (e.g. transitions are never batched in one txn).
