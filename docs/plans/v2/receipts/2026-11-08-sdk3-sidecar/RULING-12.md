## ADDENDUM — D2 (adversary round 5 / servicer F6 residual 1): under R31 reading (b), `--wave <file>::<Class>` collects the FILE, so the file's other listed ids that were not SELECTED read STALE ("renamed or deleted"). **Rule: "collected" is SELECTION-level, not file-level. An id is judged stale iff the run's selection COVERED it and it was not collected. The stale line names the selector. R31's class is kept and sharpened, not replaced.**
- The class R31 (b) stated was *"stale only within what this run actually looked at"*; "its file was collected" was the first approximation of "looked at", and a `::Class` selector shows it is too coarse by exactly one level. pytest's own notion of what a run looked at IS the selection: a selector is a node-id prefix on `::` boundaries (`file`, `file::Class`, `file::Class::test`, with `[param]` the leaf). So: `in_scope(id) := any(selector == id or id.startswith(selector + "::") or id.startswith(selector + "[") for selector in selection)`; a FULL run has an empty selection = everything in scope, which is (b) exactly; a scoped run judges only what it selected. `wave_gate` already forwards the selectors verbatim and refuses `-k`/markers/worker counts (read: "verbatim, no -k"), so selection = node-id prefixes only and "selected ≠ collected" can only mean renamed/deleted — the premise the stale verdict needs. ⚠ Say explicitly in the code and the pin that this prefix walk decides SCOPE ("did pytest look here?"), never ADJUDICATION — MP-F6-2 (no hierarchical matching for ownership) stands untouched; the two questions are different and the F6 contract pins them separately.
- R17 Leg 1: the stale line must answer the question it measured — *"of the ids this run SELECTED, which no longer exist?"* — so it reads `<id>: selected by '<selector>' and not collected — renamed or deleted; confirm with --collect-only before deleting the entry`, and a scoped run's render already carries the SCOPED-RUN flag. An id outside the selection gets NO verdict (neither stale nor adjudicated nor self-destructed — the same third state R33 gave a collected-but-skipped id): registration kept, nothing said. Leg 2 (the forgery that prompted this): `--wave file::ClassA` with a renamed id in ClassB served "renamed or deleted" → an agent deletes a live registration → the next full run reads that red RED_ORPHANED, or worse the agent "fixes" the registry wholesale. Under selection-level scope that state serves no stale line at all.
- Pins (servicer, MP5-D2, F6 contract): (1) `--wave file::ClassA`, listed ids in ClassA (one renamed → STALE naming the selector) and ClassB (untouched → no verdict, registration kept); (2) CONTROL `--wave file` → ClassB's renamed id IS stale; (3) a full run (no selection) behaves as (b) byte-for-byte on the existing fixtures; (4) a `[param]` leaf selector covers only that parameter; (5) a listed id whose file is outside every selector → no verdict (R31 b, unchanged). Wrong builds the pins must kill: file-level scope (the current reference); selection used for ADJUDICATION (a class selector "owning" its members — must stay RED under MP-F6-2's pins); a scoped run with no selection recorded treated as full.
- Who edits: the gate change (a `selection: tuple[str, ...]` carried from `wave_gate`'s forwarded args into the pytest leg's stale test) is PRODUCTION `scripts/` → the builder, inside F6 build step 0 (it is one predicate on the same function R31 changed); the pins → the servicer, before the registration lands (R32's rule). Named bound, stated in the stale docstring: a selector pytest expands differently from the prefix walk (a directory path, a `::` inside a param string) is not recognised and reads as "not in scope" — fail-safe toward silence, never toward a false stale; trigger: `wave_gate` ever accepting a selector shape beyond file/node-id.
