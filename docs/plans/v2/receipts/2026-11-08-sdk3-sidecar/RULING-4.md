# design-sidecar-66 — ruling 4: R23 servicing channel — mechanics CONFIRMED, six holes closed

brief-base v25 read · 2026-11-08

R23 (builder never edits tests; a long-running Opus contract author services requests) is the operator's and is the right shape: it restores brief-base §2's role boundary and keeps my R22 riders where they bind. The channel as described — builder → `lore_comms send` + native wake → at-rest servicer → reply on thread → builder drains at turn boundaries — has these holes:

1. **The builder's request is a CLAIM about the cause, and the builder is the one party motivated to call a red "SDK 2.0".** Rule: the servicer REPRODUCES before ruling — runs the named node on the current tree itself (haiku-runner), reads the traceback, and classifies the cause independently. A request body carries only node id + one-line claimed cause + a path to the builder's failure log (refs; the 4000-char body cap forbids tracebacks). A verdict that cites the builder's log without the servicer's own run is void.
2. **REMOVE is the escape hatch, and the servicer is its own only grader (the adversary budget is spent).** Rule: a REMOVE verdict row's fate must be `carried-by <existing pin node id>` or `retired-with drop-list row #N` (an operator-approved row). A REMOVE with neither fate is a FORK the servicer raises to me before editing, not after. REWRITE rows need the carried behaviour named the same way (R22 rider 2). REFUSE = "red for a product reason" → back to the builder with the traceback; the servicer never touches production code.
3. **Shared working tree (no worktrees, operator standing rule): both agents edit and test one tree.** Rules: the servicer commits ONLY test paths (`git commit -- <test paths>`), never stages production files; its RED/GREEN receipts carry `TREE=` and are void if the builder edited during the run — so the servicer's pre/post runs are the targeted node set only (seconds, not minutes), and the builder is briefed not to commit while a servicing run it was told about is in flight. The authoritative both-ways diff (R22 rider 1) is computed ONCE at the cold audit over the whole packet — test tree at the pre-build base vs final production → R1; final test tree vs final production → R2 — so interleaving does not corrupt it; per-request receipts are attribution, not the gate.
4. **The builder waiting = idle, and idle reads as done/stalled to the lead's gate.** Rule: the builder never blocks on one request — it posts, continues other build items, and drains at boundaries. When blocked ONLY on servicing, it arms a `Bash(run_in_background)` watcher on the servicer's ARTIFACT (a commit touching the requested test file: `until git log <base>..HEAD -- <path> | grep -q .`), the one channel measured to reach a busy agent mid-chain (brief-base §5), never a poll of the inbox and never repeated `lore_comms await` turns. Proof of service is the commit, not the reply.
5. **The servicer's idle is benign and must not be gated or wake-looped.** Rules: it writes `{"artifact": null}` to its idle-gate contract at spawn (same as the sidecar); registers on `lore_comms` with a cadence; drains at EVERY turn boundary (a second wake arriving while it services request 1 lands at its end_turn — fine only if it drains then). Its state lives in the ledger (am-37 rows) and its commits, so when its context fills it is respawned with a suffixed name and loses nothing.
6. **Interim reds while a request is open.** Between the builder's production change and the servicer's edit, the node is red on the shared tree and the currency gate's pytest leg would read it RED_ORPHANED. Rule: an OPEN request is itself the adjudication — the servicer registers the node under F6 `red_nodeids` (owner: servicer, trigger: the ruling commit) when it accepts the request, and the self-destruct clause deletes the row when the node goes green.

Under R17: the channel serves no agent-facing surface; what it protects is that no pin on a served behaviour is retired by the party that benefits from its retirement. No operator ruling reversed. Standing by.
