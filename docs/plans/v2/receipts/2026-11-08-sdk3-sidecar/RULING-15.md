## 1. Reachability — answer first, per door (the lead's first question)

The premise "each row gets its own `time::now()`" is true of ONE of the rollup's THREE stamp-paged legs.

| leg | stamp column | who mints it | production doors | tie by construction? |
|---|---|---|---|---|

| findings | `finding.created_at` | **PYTHON** `datetime.now(UTC)` (`findings.py` `report`, line ~643) | `report` only; batch edges touch status, not `created_at` | NO. Microsecond resolution, ns tail `000`; two `report` handlers in the server process within one µs tie. A fleet burst is the door |

Non-production doors, each named: `scripts/probe_reanchor_58.py` (single-row, engine stamp, probe only); `scripts/restore_prod_dump.py` (`POST /import` of a dump — preserves the dump's stamps verbatim, mints none: it reproduces a tie iff the source had one); the `/backups/lore` cold copies (file-level, same property); tests' forced `<datetime>` casts (the B1 pin, the tie probe). **So option (b) — "a pinned bound, if ties are unreachable through every write door" — is unavailable:** false for two legs, believed for the third. A bound resting on the engine clock is the self-sealing class (#107: "the vendor docs said so").

**And R43 owns it.** Before B1 (fda1411) a cut inside ANY page re-served row 1 forever (the servicer's HEAD log: a livelock — loud in its own way). ## 2. Verdict: **(c) — never end a page inside a stamp group. ONE shared paging helper under all three legs; the served cursor stays a plain exclusive instant; the one irreducible case is NAMED and REMEDIED, never skipped. Not a compound cursor.**

**The rule.** The leg reads `LIMIT limit+1`. If the overflow row's stamp differs from the boundary row's, the page is the first `limit` rows — unchanged. If it is the SAME stamp (a cut inside a group), SHRINK the page to the rows whose stamp is strictly below the boundary stamp `B`; the resume point is the last served stamp and `>` is then exact by construction. If shrinking leaves nothing (the group fills the page head: N rows at `B`, N > limit), serve the first `limit` of them, do NOT advance (resume = `since`), and the leg header names it: *"N rows share the stamp B; limit L cannot page past them, so this cursor does not advance — re-call with limit ≥ N"*. `limit` has no ceiling today (schema: "a positive int"), so the remedy always exists.

**Why this and not the compound cursor (a).** Both close the class — the operator's "SIMPLEST CLOSING RULE" is *a page boundary never falls between rows the cursor cannot distinguish*; (a) makes the cursor distinguish them, (c) makes the boundary never fall there. (c) wins on every law that applies: (i) the served cursor is a durable token agents hold ACROSS SESSIONS and the schema promises "an EXCLUSIVE ISO-8601 instant" — (a) changes that contract (a grammar, a parser with its own refusal pins, a legacy-bare-instant case, churn in the seven dispatch pins f8e2048 just added and the B1 pin's `_served_cursor`), (c) leaves it literally true and makes it MORE exact; (ii) the cursor is ONE instant shared by three legs with heterogeneous keys (opaque uuid4 / `number` / `seq`) — (a) needs a boundary key per truncated leg in the token, (c) needs nothing; (iii) (c) also retires a second hazard for free: the engine's ORDER-BY order WITHIN a tie is unspecified, so a cut inside a group serves a nondeterministic subset — (a) must add `, id` to every ORDER BY to be deterministic, (c) never serves a partial group; (iv) size to the risk — lore's own writers never mint a task-leg tie on 3.3.5 and a findings/messages tie needs a same-µs burst, so the `limit` exactness (a) buys is bought at the cost of a served-contract change for a case the fleet will almost never see. **Named re-open trigger → (a):** the day `limit` gains a ceiling (then a group larger than the ceiling is a true dead end), or the day a production door mints ties routinely (an importer, a bulk reaper). Record both in the helper docstring.

**R17 on the fixed surface.** Leg 1 — question answered: *every row with stamp > cursor, in stamp order, in WHOLE stamp groups, at most `limit` per leg; or, for a head group wider than `limit`, its first `limit` rows with the cursor held*. Question the consumer asks: *everything since my last call, up to `limit` per leg*. Diffs: a shrunk page shows fewer than `limit` while more exist — already named by the existing elision header, whose "resumes at the elision point" becomes exactly true; the held-cursor case — named by the new header text. Cross-leg at-least-once (another leg's rows above the min cursor re-served) is pre-existing and lives in a docstring only — see §4 Q2. Leg 2 — store × {tie at the cut, group wider than limit, distinct stamps, empty}: each CONSTRUCTED by the pins below; the forgery #591 names — *tied rows past the limit serve the bytes of "no more rows"* — is gone because the blocked header and the idle header are different bytes.

## 3. Riders (each with its requirement)

1. **ONE helper, three callers — and the reach is a checked variable.** `updated_since`, `filed_since` and `message_activity_since` today hand-roll the same `WHERE col > $since ORDER BY col ASC LIMIT n` + `count() GROUP ALL` pair three times (a pre-existing triplication; messages binds `LIMIT` as a param, the other two interpolate it — the helper picks the param form, messages' own comment says why). The tie rule goes in that ONE helper (home: `loremaster/store/` beside `_txn`, the store seam; it carries the legs' extra WHERE — the message leg's visibility filter — as a fragment). The three `*ActivityWindow` models gain the helper's two outputs — `resume_at: datetime` (the leg's exact resume stamp; `since` when held) and `held_group: (stamp, N) | None` — and `_rollup_next_cursor` reads `resume_at` instead of `rows[-1].<stamp>` (min over truncated legs; max over all legs when none truncated; a held leg contributes `since`, so the whole cursor holds and the other legs re-serve — at-least-once, consistent). Registry row in the build report: looked at `updated_since` / `filed_since` / `message_activity_since`; disposition: the three bodies become callers. **Mutation proof at audit:** disable the helper's tie branch → the pins of ALL THREE legs go red; a leg that stays green holds a private copy or has no pin (both findings). Control: restore ⇒ green.
2. **Pins — the servicer writes them (R23), the builder builds production; live store :18000, stamps FORCED through the B1 idiom (`SET <col> = <datetime> '…'`, re-read to prove the forcing landed).** Each names the wrong build it kills:
   - **P1 (#591 itself, RED before / GREEN after):** three tasks at one stamp `S`, `limit=1` → the header carries the held text with N=3, served cursor == `since`; re-call with `limit=3` → all three served, cursor == `S`; re-call → idle, and now TRUE. Walk receipt: served ids over the walk == the three ids, each exactly once. Kills: the HEAD build (skip), and a build that "advances anyway".
   - **P2 (shrink):** rows `a@S1, b@S2, c@S2, d@S3`, `limit=2` → page 1 = {a} (cursor S1), page 2 = {b, c} (cursor S2), page 3 = {d}; every page ≤ `limit`; set equality both ways over the walk. Kills: a build that extends the page to the whole group (serves 3 > limit), and one that cuts (serves {a, b}, skips c).
   - **P3 / P4 (the other two legs):** P1's shape on `finding.created_at` and on `message.created_at` (the governed leg, with a Subject capability from the `test_rollup_extension` harness). These are not optional: they are the legs whose writers CAN tie.

3. **Prose that must change with the mechanism (stale-prose class):** the three `*_since` docstrings ("capped at `limit`" → "at most `limit`, never ending inside a stamp group; a head group wider than `limit` holds the cursor and is named"); `_rollup_next_cursor`'s docstring (reads `resume_at`); the `limit` schema line ("per-leg row cap" stays true — add "a page may stop short of the cap to avoid splitting rows that share a stamp"). ## 4. Raised, not ruled — two siblings of the same class found while reading

- **Q1 — the message leg's elided tail is unreachable by cursor paging.** `_rollup_next_cursor(effective_since, task_window, finding_window)` does not take the message window; its header says "raise limit for more" but the cursor, set by the other legs, moves past the elided messages, and nothing in the render says so. Same class as #591 (a page cut the cursor does not cover). I found no 63b-ii-b text naming it as a bound. Two honest fixes, operator's call: (i) feed `message_window.resume_at` into the min (then a chatty message leg paces the whole rollup's cursor — more at-least-once re-serves of tasks/findings), or (ii) keep the exclusion and NAME it in the header ("not covered by the next cursor; raise limit on THIS call"). I lean (ii): the rollup's message leg is a summary by design — the story surface is `drain`, where nothing is lost. Either way it needs a finding row; the lead files it (I file nothing).
- **Q2 — cross-leg at-least-once is a docstring fact, not a served one.** When one leg truncates, the other legs' rows above the min cursor are re-served next call; the render does not say so. A consumer acting on a re-served task transition twice is "wrong in a way the response did not name" only if it treats the leg as exactly-once — the schema says nothing either way. Cheap to name in the elision header ("other legs re-serve rows above this point"); recommend it rides the same header edit, operator's call on whether it is R43.
