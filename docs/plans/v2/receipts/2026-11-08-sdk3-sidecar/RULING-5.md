## 1. FORK-R6-1 — `TransactionConflict` ruled a fourth fate, `retried` (author took A)

**Verdict: CONFIRM A, with three riders; B's one true half is absorbed as a rider (name the fate in §15; do NOT file the kind as `unknown`).**

- **Why A is right under R17.** Leg 1: no served surface ever needs the word "retried". A conflict either resolves — the VALUE is served — or exhausts into `TxnContentionExhaustedError`, which `_PROVEN_NO_KEY_CLASSES` and the am-37 class table both rule proven-no-key ("rolled back"): the mint note says nothing was created, retry is safe. The agent's question *"did my write land?"* is answered "no, after N attempts" — true by the engine's own semantics (a conflicted statement commits nothing; "This transaction can be retried"). Reading B as stated — "add it to §15 as `unknown`" — would be a FALSE bound on the ONE path where the kind could escape (see Leg 2): a rollback served as "outcome unknown — verify" is the safe direction, but it is still a scope diff, and B's own text ("the pin's failure text offers only proven/unknown") is a reason to fix the failure text, not to mis-rule a kind. Leg 2: the broken state that serves identical bytes is *a seam that does not retry* — the raw kind would then surface as an unspecified `TxnDomainRejectionError(kind=TransactionConflict)`, `proven_no_key` → False → the conditional "unknown" note. `test_the_seam_and_the_predicate_agree_with_the_ruling[TransactionConflict]` asserts `RetryableConflictSignal` through the REAL ladder, so that forgery is pinned; the driver-level never-retries forgery is T1/T2 (R20 A2 keeps their contention premise).
- **Rider 1 — the prose is FALSE and must be fixed in round 7 (stale-prose class, in a ruling table).** q1b's comment says *"SDK 3.0 adds `ErrorKind.TRANSACTION_CONFLICT`"* and R6.2/the hand-back say *"top level or as a Query detail"*. Measured live on the installed 3.0.0: the value exists ONLY in `QueryDetailKind`; `ErrorKind`/`KIND_TO_CLASS` do not have it. The pin is correct DESPITE the prose because the table is keyed by VALUE and `_sdk_error` builds any `QueryDetailKind` value as a detail under `kind: "Query"` — which is exactly the shape `_is_retryable_conflict_kind` (`_detail_kind`) recognises. Fix the two sentences; a ruling table that mis-describes the enumeration it adjudicates is the §8 class.
- **Rider 2 — a disjointness pin, so a future SDK cannot make the table lie by construction.** `_sdk_kind_domain()` unions top-level and detail values into ONE key set, and `_sdk_error` checks `kind in _QUERY_DETAIL_KINDS` FIRST. If a later SDK adds a TOP-LEVEL `TransactionConflict`, the domain still has one key, every cell still injects the DETAIL shape, and the top-level door is untested while the table reads as covering it — a false clear by construction (Leg 2, dependency = SDK × wrong-instance). One line in q1c, which already splits them: `assert not (_SDK_TOP_KINDS & _SDK_DETAIL_KINDS)`, failure text "a kind now exists at both levels — parametrise `_sdk_error` by (enumeration, value) and rule each door". Cheap, derived, reddens by name.
- **Rider 3 — name the fourth fate where the ruling lives.** `retried` is DERIVED from two operator rulings (R11, drop row #2: the SDK's conflict typing is the conflict authority), so recording it is within the lead's authority: add to `sdk3-rulings.md` the row *"`QueryDetailKind.TransactionConflict` → retried by the seam; sustained → `TxnContentionExhaustedError` (proven-no-key by class)"*, and mirror it into am-37 §15 (`docs/design/2026-09-26-packet64-kickoff-rulings.md`) at the operator's next pass — a mirror, not a new ruling. The q1b failure text that "offers only proven/unknown" gains the third word.

## 2. FORK-R6-2 — ruling tables and the a19 hostile-id refusal pins go RED at HEAD by design (author took A)

**Verdict: CONFIRM A. B (version-branch them like the old F-a fakes) is rejected.**

- Reason. R21 already removed the version-aware interim for the FAKES; the same logic binds PINS harder: a pin branched on the installed SDK asserts two different worlds under one name and cannot fail in either until the branch is removed — it is the F-a interim's hazard with no builder commit scheduled to delete it. A ruling TABLE branched by version is two tables wearing one name; the am-37 completeness pin's RED at HEAD ("ruled class the taxonomy no longer defines") is the HONEST state of HEAD, which lacks the class. Under R17 the a19 hostile-id refusal pins are SERVED-surface pins: branching them would mean the forbidden `str(RecordID)` serving is "accepted on SDK 2.0" — a pin blessing on one world the exact rendering R7(d) forbids on the other.
- Rider (R22 rider 3 / R24 #6, already law): the RED@HEAD set is DECLARED from `--collect-only` before the run (round 6 did this) and REGISTERED under F6 `red_nodeids` (owner: SDK3 builder; trigger: the build commit), with the count stated in the round-7 receipt — so currency never reads RED_ORPHANED in the interim, and the self-destruct clause deletes the rows when the build lands.
