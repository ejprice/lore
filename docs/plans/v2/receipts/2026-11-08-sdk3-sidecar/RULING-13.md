## FORK T — **use the SDK's `with connection.timeout(TEARDOWN_KILL_TIMEOUT_SECONDS): await connection.kill(id)`; the six test doubles gain a `timeout()` through ONE shared mixin (servicing request). `asyncio.timeout` is the hand-rolled twin in this position.**
- **Does the SDK's facility do the job? Yes, and it covers the exact wait the builder is bounding.** The park the builder describes is `kill()` → `_await_reconnect()`, which waits on the reconnect task with `timeout=self._request_timeout()` — the same per-request budget `connection.timeout(N)` overrides through its ContextVar — and raises the SDK's typed `TransportTimeoutError` when it expires; the reply wait in `_request` is bounded by the same budget. So the override bounds BOTH halves of a kill on a dropped socket, in the SDK's own typed vocabulary. Bound, stated: the two halves each get the full budget, so the worst case is 2·N (≤ 4 s at N = 2), not N — write that into the constant's docstring; a tighter total needs N halved, not a different primitive.
- **Why `asyncio.timeout` is the twin, not the right primitive here.** It would be the right primitive for bounding an await the SDK does NOT own; this await IS an SDK request, and R5 F4b (operator) names `with db.timeout(N)` as THE mechanism for a named constant override — a teardown bound is a named constant applied to one request, squarely that shape. Two concrete differences, both against the stdlib form: (i) cancellation vs typed raise — `asyncio.timeout` injects `CancelledError` into the SDK's own coroutine at whatever await is current, a path the SDK shields CALLERS from (`_await_reconnect` deliberately uses `asyncio.wait` so `close()`'s cancellation "must not reach a caller nobody cancelled") but did not design to RECEIVE; the SDK's timeout raises on its designed path and pops its pending entry in `finally`. (ii) classification by accident — the builder's swallow works because stdlib `TimeoutError ⊂ OSError ∈ _CONNECTION_ERRORS`; that is a transport classification that happens to be true by inheritance, not a decision the seam made ("routing is not sharing", in the error lattice). With the SDK's `TransportTimeoutError` (a `SurrealError`) the swallow is the designed one.
- **The doubles argument is a cost, not a fit.** Six fakes have `kill()` and no `timeout()`: add `timeout(seconds) -> contextlib.nullcontext()` ONCE, as a mixin in `sdk3_shape_fakes` (the home of the SDK-shape helpers), and have the six inherit it — one implementation, not six copies; a servicing request under R23. Rider: both `_safe_kill` sites keep their existing REQ-D bound pins (elapsed ≤ bound + margin on a dropped socket); mutation at audit: drop the `with connection.timeout(...)` ⇒ the bound pins redden (the kill parks 30 s). Note for the record (both primitives alike): a timeout anywhere in `kill()` skips `_end_live`, so the client-side live registration is not ended by the kill — harmless in lore because `_teardown` cancels the consume task independently; state it in the `_safe_kill` docstring rather than discover it later.

## FORK S — **drop-list #16: RETIRE the 18 `_safe_close` wrappers (fate R), with R1's rider — a live retirement pin that FAILS if the guard is still needed, proven by a mutation that re-introduces the old symptom. Do not keep 18 clones; if the operator wants a belt, it is ONE `close_quietly` in `_txn`, never 18.**
- **R8's own rule decides the fate.** #16 is a C row whose named measurement was "close() over a severed socket never raises on 3.0" — measured 40/40, both sever modes; a C row's condition met ⇒ R. The guard's origin is sdk-bug (SDK 2.0's `close()` on a dead socket raised `websockets.ConnectionClosed*`, store reference §3), re-probed gone — R1's literal case for `retire`. And the SDK's `close()` is DESIGNED not to raise: idempotent by docstring, usable from a foreign loop, it cancels its own tasks and wakes its queues before `_teardown` (read) — the measurement confirms the design rather than carrying it alone.
- **"Would a delete make the next SDK regression a crash on close?"** That question is exactly what R1's rider exists to answer, and the answer is: no — it makes it a RED at upgrade time instead of a crash in production. The pin: through the existing L-family instrument (proxy `go_down()`, then `_close_owner`), every DERIVED owner's `close()` completes without raising on a severed socket, both sever modes (the owner set is the one L1/L6 already derive, so a new owner joins at collection). The mutation that proves the pin discriminates: monkeypatch the SDK connection class's `close` to raise `ConnectionUnavailableError` ⇒ with the wrappers gone every owner's `close()` propagates ⇒ the pin reds for every owner (declared set = the derived owners); restore ⇒ green. That red IS the "SDK regression on close" the lead fears, caught by the suite. Second layer, already present (R5.1's 39-site table): every lifecycle call of these `close()`s sits under a composition-root CLEANUP catch (`server.aclose` ×2, `build_app_context` ×3, `scout.aclose`/`run`, `loopback._loud_teardown`) — a close failure there is logged, never a crash; the per-owner wrapper was a second, inner guard around a condition that no longer occurs.
- **Why "keep all 18" is not the safe choice it looks like.** Eighteen bodies carry a 4-line policy ("swallow a dead-socket close") with the reason "the socket is already gone" — a reason measured false on this SDK, taught eighteen times: the stale-prose class, and eighteen clones of one policy (ONE IMPLEMENTATION). Behaviour-invisible is not cost-free when the invisible thing is wrong teaching. If the operator still wants a belt against the unmeasured paths (close during an in-progress reconnect, close from another loop — both DESIGNED safe per the SDK docstring, not probed), the belt is ONE function, `_txn.close_quietly(connection)`, called from the 18 sites, with its own single pin and the reason "SDK 3.0.0 close() is designed not to raise; this guards an SDK regression" — then it is a stated bound, not a stale workaround. Recommend R; the belt only on the operator's call.
- **Who pins what.** Production (18 `await self._safe_close(c)` → `await c.close()`, 18 `def` deletions; X18's nested-close bodies untouched — their pins stand): the BUILDER, this build, before the cold audit. The retirement pin + its declared mutation: the servicing author (R23). Note the pin's shape: it is GREEN on both HEAD and the build (nothing raises either way — on HEAD the wrapper swallows, on the build the SDK does not raise), so its discrimination lives entirely in the MUTATION — declared from `--collect-only`, run by the servicer on a scratch copy, receipt in the inventory row (fate R, `retired-with drop-list row #16`, carried-by the new pin). A green pin with a held mutation is the correct shape for a retirement (R1's rider), not a weak pin. The cold audit re-runs the mutation.

## ADDENDUM (#19077) — the awaiter's `except _SDK_AWAIT_BOUNDARY_ERRORS: pass` around `connection.close()` in `InboxAwaiter._teardown`, and the owner pin's reach

**1. Not #16's sibling — a DELIBERATE guard, re-classified; KEEP it, rewrite its reason, replace `pass` with a debug log.**
- Context decides it. The 18 retired wrappers guarded LIFECYCLE closes that already sit under composition-root cleanup catches; a raise there is logged by the root. The awaiter's close sits inside a SERVED verb's teardown (`await_inbox`'s finally path): if `close()` ever raised there and nothing swallowed it, the raise would REPLACE the verb's computed answer — the agent asked *"did anything arrive?"* and would be served a connection error about a connection it never knew existed (Leg 1: a false failure on the served surface, the F14/D1 class from the other side). So this swallow is not "the socket is already gone" (SDK 2.0's reason, now false); it is *"a teardown fault never replaces the verb's answer"* — origin `design`, fate `keep` in R1's columns, and the inventory row for #16 gains that line. Riders in the same bullet: (i) `pass` → `logger.debug("inbox_awaiter.teardown.close_failed", exc_info=True)`, because a bare `pass` is the one shape under which the SDK regression the lead feared would be INVISIBLE forever — the debug line is the trace; (ii) the pin: sever the socket AFTER the drain and BEFORE teardown (one leg in `test_comms_await::TestSocketDropNonLoss`'s family) ⇒ `await_inbox` still returns its drained answer, no raise; (iii) the CONTROL that proves the two decisions are deliberate and different: under the SAME mutation (SDK class `close()` monkeypatched to raise) the owner pin reds for every owner (wrappers gone) while the awaiter leg stays green (guard kept) — recorded together as one receipt.
