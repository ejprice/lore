## Round 5 — two scouts, same branch, different machines (two devs on staging)

brief-base v7 read.

**1. The race, precisely.** It exists **iff `feed` is a KIND rather than an INSTANCE** — i.e. iff both scouts resolve to one view key `staging`. Then both write one view and you get **last-writer-wins per FILE**, so the view becomes a **chimera: file X from dev-1's tree, file Y from dev-2's, a state that exists on no machine and in no commit.** That is the worst class we have discussed — not stale, not empty, but internally plausible, correctly cited, and **reproducible by nobody**; there is no tree anyone can check it against. It also *flaps*: identical queries return different answers as writes interleave, with no sha change to explain it. And note the divergence is not only uncommitted — different pulled commits means even the committed baseline differs.

**2. Resolved by IDENTITY, not locking or merging.** Locking is wrong: it serialises two legitimate realities into one slot and merely changes who wins. Merging is worse: there is no merge — two trees, and merging manufactures a third fiction. **Invariant: a view has exactly ONE writer; a branch NAME is not a view identity.** So `staging@scout-a` and `staging@scout-b` are two sibling views, both honest, and the race is dissolved by construction rather than arbitrated. Enforced at **packet 17's identity/registration seam** (it is an identity question, so 17 owns it), the store-level single-writer uniqueness on the triple in **23**, and the authorization half — a scout may write only its own view and cannot claim another's — in **39** (my §3 view-scoped write grant, now doing double duty).

**3. Session binding: "staging" becomes AMBIGUOUS, not defaulting.** A user declaring bare `staging` while N instances serve it gets a **refuse-and-teach naming the candidates** (`staging@scout-a` last seen `T1`; `staging@scout-b` last seen `T2`), never an arbitrary pick. That is my no-default rule generalised from *no default view* to **no default DISAMBIGUATION** — same principle, same reason: an arbitrary pick returns the right filenames with the wrong bodies. Renders always name the instance, so one branch on two machines is never visually one thing. And `origin/staging` ref-fed is a legitimate THIRD view — shared, unambiguous, and the right candidate to offer first.

**4. One word changes: `feed` → `feed-instance`** (scout identity, not scout kind) in the rider — identity = `(parent, ref, feed-instance)`. Nothing reverses. This is the third bound I stated that collapsed on contact with a new topology, and the pattern is now the consult's real finding: **every absolute I offered was an absolute about the topology I happened to be picturing.** The identity tuple earns its keep precisely because it converts each of those silent premises into an explicit, rendered component.

**VERDICT:** this is not a concurrency bug to be locked away but an identity bug — make `feed` an instance and the two-devs-on-staging race cannot be expressed, let alone raced.
