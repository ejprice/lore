## Round 2 — long-lived branches + branch-in-place (pre-hosted framing)

**A — long-lived branches (main/staging/dev), main checked out.** Real questions: "what does function Y look like on staging" (known file) — I'd `git show staging:path` directly; git answers this precisely and instantly, route around. "Does staging already have a fix/helper for X" (unknown location, semantic) — genuinely lore-shaped IN PRINCIPLE, but lore has no tree to search there today: no working directory, no watcher on that ref. In practice I'd checkout staging into a scratch worktree and search that, or ask a teammate — I would not expect a standing "search anything in git" surface to exist for free.

Designer: this does NOT slot into the v1/v2 delta-overlay table — it's not a delta problem, it's "materialize a full index for a ref nobody has checked out," per branch, indefinitely. That's the same cost shape the operator BANNED for worktrees ("full-tree indexing... BANNED," `17-worktree-overlay-design.md:14`), applied to a branch instead — arguably worse since main/staging/dev are long-lived, not short-lived. It does not reverse "ref-vs-ref via `lore_diff` is never" (that ruling is about the compare VERB; this is about content AVAILABILITY, a different axis) — but supporting it would need its own operator-ruled design (e.g. an explicit opt-in registered-branch index, its own reap/refresh/cost story). **Flagging as a genuinely open, unruled question — not a recommendation.**

**B — branch-in-place (`git checkout -b` in the SAME watched directory, overlay never engages).** Real question: "diff my edits vs main." I'd try `git diff main...HEAD` first for the textual diff — same as always, git wins there. But for symbol-level deltas, `lore_diff` is genuinely useful HERE — unlike the ref-vs-ref case — because I verified: snapshots stamp `git_branch`/`git_ref` at capture time (`SnapshotSummary._row_to_summary`, `loremaster/loremaster/diff.py`), and a snapshot auto-stamps after EVERY fully-successful sweep (`_maybe_stamp_snapshot`, `loremaster/loremaster/index/indexer.py:1191-1210` — skipped only on a no-op or partially-failed sweep). Since the watcher just tracks whatever is checked out at the root, a sweep that ran while `main` was checked out already left a snapshot labeled `git_branch=main`. After `checkout -b feature` + edits, `lore_diff(since=<that main snapshot>, until=None)` diffs main's recorded state against the LIVE (uncommitted-included) state, with real `function_deltas` — **zero new mechanism needed.**

**Verdict.** B does not reverse the ref-vs-ref-never ruling and needs no new tool — the one real gap is that nothing GUARANTEES a main-labeled snapshot exists at the moment of branching (only true if a full-success sweep ran while main was checked out). Two options, not smuggled as one: (i) cheap — a render-level nudge (`lore_index`/`lore_diff` teaching "no main snapshot found, stamp one before branching next time") — fits existing machinery, v1-adjacent; (ii) heavier — an auto-stamp-on-branch-change trigger, which IS a new mechanism I'm not recommending, just flagging. A does not slot into the existing table at all and is a separate open design question for the operator — supporting it is a materially bigger ask than anything packet 17/23 scoped, closer in shape to the banned full-tree-indexing case than to the delta overlay.

Fixture with disjoint file sets across agents would NOT discriminate — no collision to catch a leak.

**2.** Stacked. Flattened re-embeds nose-cheese's shared delta up to 3× and drifts independently per leaf when nose-cheese itself advances. Stacked keeps ONE nose-cheese overlay all leaves chain-walk (ONE-IMPLEMENTATION law). Yes — rider (a) needs the parent pointer NOW: identity = (parent, ref-or-path), parent defaulting to `base`. Every view names FEED KIND + LAG + LIVENESS: ref-fed (git-sync) discloses sha + fetch age; scout-fed (fs-watch, local-laptop or in-container) discloses last-ingest age + scout-liveness — a disconnected scout must render as STALE, never as "current-but-old" (different failure classes: bounded lag vs indefinite silence). The sha-keyed reconcile that already collapses full-tree watching to delta-only ingestion is reused unchanged either way.

## Round 5 — two scouts, same branch, different machines (two devs on staging)

**1.** The race exists whenever view identity is keyed on BRANCH NAME ALONE (e.g. `view_id="staging"`). Branch name is a human label, not unique across machines — two scouts both ingest into the SAME namespace. Served result: file-by-file last-write-wins between two independent, legitimately-divergent working trees — a query against "staging" can return a Frankenstein composite neither machine's tree ever actually held (same shape as this repo's hot-row-mint contention law, generalized from a DB row to a view namespace).

**2.** Not locking, not merging — both would be actively wrong (the two trees are SUPPOSED to stay independent until pushed). Fix is IDENTITY: add a SCOUT/OWNER component whenever `feed=fs-watch`, so two scouts declaring "staging" mint two DISTINCT views, never one shared one. Enforced at packet 17/23's view-REGISTRATION seam (same surface OQ2/rider (a) already touch) — mechanism, not auth. WHO may register as which owner stays 39's seam, consistent with keeping auth out of 17.

**3.** A bare "staging" render must never silently resolve to an arbitrary scout's copy — that's the silent-disambiguation cardinal failure (trust doctrine). Within one session bound to its OWN scout, default-to-own-view is fine and should disclose "staging as seen by scout X" explicitly; across scouts, ambiguity must be SURFACED (forces a scout-qualified choice), never guessed. This sharpens OQ2's no-new-tool preference: default stays session-scoped, but "session" now must resolve through the calling scout's owner id, not branch name.

**4.** Yes — rider (a) gains a component: identity = (parent, source, feed, **owner**), owner REQUIRED for `fs-watch`, optional/canonical-singleton for `git-sync` (per `MASTER-PLAN.md`'s singular "a git-synced repo" — flagging that assumption as unverified if multi-region git-sync ever exists, not resolving it here). No other prior answer reverses.

**Verdict:** the fix is identity, not concurrency control — add owner/scout to the key now, before any multi-machine registration ships.
