## 5. Defects and flags

**DEFECT-1 — a measured number with no reproducible instrument (`:904`).** Not a citation problem
that a repoint fixes; the *measurement* is unreproducible. `30.2%` at 16-way, raw SDK, pre-fix, is
cited in production prose as the justification for logging only terminal dispositions. My proposed
edit above is honest about the gap rather than laundering it, but **I am flagging this as the
operator's call, not mine**, because there are two defensible readings and they produce different
edits:
- *(a)* Repoint to `#102` + admit the probe is absent (what I drafted). Preserves the number, admits
  it is unverifiable.
- *(b)* **Strike the number entirely** and keep only the qualitative claim ("contention is the
  NORMAL case"), which the committed survey *does* support (p50=2 attempts at every N ≥ 8 means
  conflicts are routine). This is more honest and loses nothing load-bearing.

**I would pick (b).** The number's only job in this comment is to justify "don't log every retry" —
and the committed survey justifies that just as well, with an instrument anyone can re-run. Keeping
an unreproducible figure because it is precise is exactly the "inherited number is a rumor" trap.
But striking a measured number is a scope call I will not make unilaterally.

**FLAG-2 — this file has a documented history of a *false* claim (#151), and I checked for more.**
Every claim I could cheaply verify against the tree held up: the ten `_query` owners are enumerated
correctly, `#93`/`#102`/`#108` are real, both cited test names exist, `JsonFormatter` writes
`record.name` as claimed, `193/640 = 30.2%` is arithmetically correct, and
`scripts/survey_txn_contention_102.py` is tracked. **I found no second #151.** Caveat stated
plainly: I did **not** run the suite or probe the engine — this is a static consistency check, so
"no false claim found" is bounded by that, not a clean bill of health.

**FLAG-3 — the two-readings site (19, `adversary R-3, latent`).** Reading A (mine): PROVENANCE, the
failure mode is fully inline and checkable against the code. Reading B: LOAD-BEARING, because
"latent" signals the adversary *built* a hoisted-out wrong build and observed the double-apply, and
that receipt is gone. I picked A because unlike site 14, the hazard here is visible by reading
`_attempt()` — `acquire()` is textually inside the closure at `:1090`. A reader can settle it in
five seconds. If the operator prefers B, the repoint target would be the same `test_retry_seam.py`
family.

**FLAG-4 — sizing the whole of #152.** My file is 24 of the finding's 61 production sites, and my
ratio came out **21:3 provenance:load-bearing (87.5% leave-it)**. If that ratio roughly holds
across the other 12 files, the entire #152 fix is on the order of **~8 minimal repoints repo-wide**,
not 61. That supports #152's own "LOW, not urgent, never a bulk rewrite" framing — and it means the
*separate* 139-site test-tree population is very likely mostly provenance too. Not my call; raising

**FLAG-5 — the 24 vs 28 gap is itself the #152 lesson recurring.** The brief's pattern was already
"bare" by the usual standard, and still missed four sites, because it was bound to a *vocabulary*
(agent names) rather than a *form* (citation-shaped labels). Per repo law — *"when you catch
yourself enumerating what is FORBIDDEN, you have already lost"* — the durable instrument here is not
a better name list. It is an **allowlist**: a repo-local pin asserting that every `(...)`-style
attribution in production prose resolves to a durable address (a `#NNN`, a tracked path, a commit
SHA, or an in-tree symbol), failing loud on anything else. I did not build it (read-only, and it is
a design question beyond my scope), but I flag it as the thing that would close #152 as a *class*
rather than as 61 individual edits.
