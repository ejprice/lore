**ESC-1 — R2's execution vehicle vs `DEPLOY: no` and the production-store boundary. [HIGHEST — a wrong choice either invalidates R2 or writes to production unruled.]**
The design is silent here. The packet says the lab validation is "an in-container one-shot verb" on "lore's instance", the header says **DEPLOY: no**, and the entry check says spike-surreal `:18000` is the test store, **NEVER `:18500`**. But R2's entire value is lore's REAL corpus, which lives in the production store — and the run also implies (a) the NEW table's DDL landing on the production store before 11-ii, (b) measurement rows + possibly an adopted head written there, (c) possibly a `measurement_failed` finding filed there. The currently-deployed container does not contain the new engine, so "in-container" cannot mean the serving container without a deploy. Candidate readings a builder could silently pick: run against spike (→ R2 measures the wrong corpus and the consult judges on garbage); run host-side against `:18500` (violates the #166 architectural shape AND #177's coordinate-hazard posture); run via an ephemeral container from the NEW image against `:18500` (the packet-01a precedent — my read of the least-wrong shape, but it is a production write from not-yet-audited code and NOBODY has ruled it). **Recommendation, not a ruling:** the lead should rule the vehicle explicitly (my suggestion: ephemeral container from the new image, post-cold-audit, coordinate passed explicitly — never defaulted — with the DDL reviewed against capabilities §1 as part of the audit), and the contract should pin that the verb REFUSES to run without an explicit store coordinate (no default; A2's mistyped-coordinate hazard).

**ESC-2 — Bootstrap mechanics are under-specified for a determinism pin. [HIGH — silently chosen, they change the CI, and the CI is the adoption test AND the 11-ii entry gate.]**
Three sub-gaps, each with two readings producing different code:
(a) *Resampling unit and "jointly"* (D1: "resample the answered union AND the absent set jointly"): paired per-probe resampling (each resampled probe carries BOTH its legs — they come from the same search call and are correlated) vs independent resampling of two sets. These give different CIs. My reading: paired per-probe, because the legs are constructed from one call — but that is a reading, not a ruling. Also: do identifier probes (no absent leg) resample in the same draw?
(b) *RNG seed derivation*: the bootstrap needs an RNG; the determinism control needs it seeded deterministically (and repo workflow law already bans wall-clock/random seeds in adjacent contexts). Seed from what — corpus snapshot fingerprint + instrument version + (B, N)? Unstated. An unseeded bootstrap breaks bit-exactness in the ARITHMETIC layer and falsely attributes the red pin to TEI (poisoning E5's leg-recording).
(c) *CI estimator*: D8 pre-registers "central 90%" but not the estimator (straight percentile of the B floors vs anything fancier). The pre-registration should name it or the adversary cannot attack it.

**ESC-3 — The ≥98% decision-agreement gate's denominator. [HIGH — a lenient reading passes the gate trivially, gating a noisy floor into 11-ii.]**
D2: "verdict decisions computed at ci_low vs ci_high agree on ≥98% of the union's samples". Which union — answered + absent only? + identifiers? On lore, + legacy groups? And do anchor-carved samples (which can NEVER flip, by the predicate's carve-out) sit in the denominator? Including a large never-flips population inflates agreement mechanically. My recommendation (labeled): denominator = the portable union (answered + identifier + absent legs), anchored samples INCLUDED but their count REPORTED beside the rate, so the gate is honest about how much of its denominator is structurally frozen. Needs a ruling either way.

**ESC-4 — The probe manifest's persistence home. [MEDIUM-HIGH — D4 is unimplementable without it; its shape is a schema decision.]**
D4's surviving-probe subset requires the PRIOR run's per-probe (point_id, probe-text sha) to be readable at the next run. Neither §7's field list nor D7's additions name a probe manifest or its home (in-row array vs side table vs run artifact). With N potentially in the hundreds-to-thousands, in-row vs side-table is a real schema fork (B4 governs whichever is chosen). Also determines whether the determinism-control identity (surviving ≡ full on an unchanged corpus) is pinnable.

**ESC-5 — Identifier-probe sampling under D2. [MEDIUM-HIGH — D2 convicts `sample_identifier_queries`'s every-Nth rule by name, but the replacement key doesn't fit identifiers.]**
D2's hash-stable key is `point_id` — per-CHUNK. Identifier probes sample DISTINCT identity STRINGS across chunks (one identity ↔ many point_ids), so point_id-threshold membership is ill-defined for them. Readings: (a) hash-stable membership keyed on `sha512_hex(identity_string)` under a threshold; (b) identifiers derive from the already-sampled chunk pool; (c) every_nth survives for identifiers only (contradicts D2's defect trace — the phase-shift jump is exactly an identifier-set discontinuity). The builder must not pick silently. Related: does `IDENTIFIER_QUERY_COUNT = 15` stay fixed-N while answered-N floats with the noise curve?

**ESC-6 — Full-pool enumeration through a bounded `scroll`. [MEDIUM-HIGH — a silent cap here biases the pool and violates the no-silent-caps law.]**
`SurrealStore.scroll` takes a REQUIRED limit, has NO cursor/pagination, and orders by record id; the survey's existing constant is `IDENTIFIER_SCROLL_LIMIT = 20_000` (verified at source). D2 requires membership computed over the WHOLE corpus's chunks; a corpus exceeding the limit truncates silently, biasing membership toward low record-ids. Options with different blast radii: add pagination to `scroll` (a store-seam change — must be escalated, it's a shared seam); a dedicated exhaustive-enumeration read (new store method, B4-adjacent); or an explicit counted, logged, REFUSING cap (run fails loudly if the pool may be truncated). Repo law: "if a workflow bounds coverage, log what was dropped — silent truncation reads as covered-everything."
